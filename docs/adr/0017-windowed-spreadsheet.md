# 表格窗口化：大文件走只读窗口视图，编辑仍交给第三方网格

体积闸门（[ADR-0016](./0016-preview-size-guard.md)）只是止血：阈值以下的文件仍然是「整份读进内存 →
每个单元格一个对象 → 整张网格」。[实测](../agents/perf.md)：152 MB CSV 要 9.7 s 和 1.36 GB 堆，峰值
约文件大小的 9 倍；25 MB 的 CSV 也要 2–3 s。要真正把上限往上推，只能改成按窗口取数。

## 决定

**分成两条渲染路径，按文件体积选择，而不是替换现有编辑器。**

- **编辑路径（保持现状）**：`x-spreadsheet` 是成熟的第三方网格，写侧能力（样式、合并、公式、校验、
  另存为）都在它身上。按「原生/第三方已做好的不重复实现」的既有规则，不动它。
- **只读窗口路径（新增）**：文件超过「窗口阈值」（初始 8 MB）时，改用只读窗口表：固定行高 + 合成
  滚动高度，只渲染视口内的行；查找、排序、跳行都在数据源上做，不碰 DOM。这条路径不提供编辑，
  与 parquet 查看器的取舍一致。

两条路径共用同一个数据源抽象：

```ts
interface SheetSource {
  rowCount: number;
  columnCount: number;
  /** 返回 [start, end) 行的显示文本，调用方只请求视口附近。 */
  readRows(start: number, end: number): Promise<string[][]>;
}
```

两种实现，因为容器格式的可寻址性不同：

- **文本源（CSV/TSV）**：真正的流式。先扫一遍字节记行首偏移（与 JSONL 的索引同一套思路：
  1 MB 分块、只留偏移），再按行窗口解压/解码所需字节。内存是「偏移表 + 一个窗口」。
- **工作簿源（xlsx/xlsm/xls/ods）**：zip 容器里的 deflate 流不可随机 seek，所以仍然整份解析，
  但**只解析成紧凑列存**（`string[]`/数字列，不建每格对象），网格按窗口取。收益来自两点：
  不建每格对象（内存从 ~9 倍降到 ~2–3 倍），以及不渲染整张表。

## 为什么不是其他方案

- **给 `x-spreadsheet` 打补丁做虚拟滚动**：它的数据模型是「每格一个对象」，虚拟滚动只解决渲染，
  不解决内存；而且改第三方编辑器会把「第三方原样保留」这条边界弄糊。
- **直接换一个开源虚拟表格**：等于为只读预览引入第二套网格实现，写侧能力还得继续维护
  `x-spreadsheet`，两套并存。
- **后端解析（宿主进程）**：webview 仍然要拿到数据，IPC 反而多一次序列化；宿主也没有比 webview
  更快的 JS 引擎。

## 后果

- 阈值以上的文件**不可编辑**（只读预览 + 「在 VS Code 中打开」）。这是产品取舍，写进 README 的
  「不支持」一节；需要编辑大文件时用原生编辑器或专用工具。
- 阈值以下的行为完全不变，闸门（ADR-0016）继续兜底。
- 分阶段落地，每阶段独立提交、可单独回退：
  1. ✅ `SheetSource` 抽象 + 文本源的字节索引与窗口读（纯逻辑，单测覆盖）；
  2. ✅ 只读窗口表组件（固定行高、合成滚动、视口渲染）+ 视图切换规则（`sheetViewFor`）；
     实测 21 MB CSV：首屏 477 ms、堆 33 MB、DOM 里 42 行；`verify:perf` 已加这条断言。
  3. ⬜ 查找/跳行接到数据源上；
  4. ⬜ 工作簿源的紧凑列存（替换当前每格对象）；
  5. ⬜ 阈值调整：窗口阈值 8 MB 与 ADR-0016 的 25 MB 上限之间目前只差一档，阶段 4 完成后
     再把上限提高（或移除），并同步 README 的「已知限制」。
- 性能闸门需要一条新检查：窗口路径的首屏耗时与堆不随文件大小线性增长（用一个 50 MB CSV 验，
  断言首屏 < 2 s、堆 < 200 MB）。这条在阶段 2 落地时加。
