# 独立演进：把上游从「必须可合并」降级为「参考资料」

ADR-0001 把「保持 `git merge upstream/main` 可行」写成了硬约束，于是头几笔提交不敢改写上游文件、`.prettierrc` 绕开 `src/`、`tsconfig.json` 明知有问题也不修。这个约束的收益是「免费吸纳上游改动」，但实际发生的不是这样：fork 已经独立演进（自有身份 `chaowu21.office-viewer-plus`、自有发布流程、两个自有 viewer），上游过去 12 个月 554 个提交里，绝大多数落在我们不改的 excel / gitHistory / vditor 上。真正需要的上游改动很少，而且往往是我们自己已经先修过的问题（zstd）。维护一个「随时可合并」的姿势，代价是持续的自我限制和一批不敢修的技术债。

## Considered Options

- **继续定期 merge**（原 ADR-0001 的做法）：冲突成本高，并且会把上游的类型错误、telemetry 残留、已删功能的配置一并带回来。
- **彻底切断**（删掉 `upstream` remote）：干净，但丢掉一个免费的实现参考——上游仍在处理 epub / excel / git 历史这些我们暂不投入的领域。
- **独立演进，上游只读**（本决策）：需要上游的某个修复时，读它的 diff，自己重写一遍，而不是合并它的历史。

## Consequences

- 上游文件可以改写，不再需要「能新增就不改写」。取而代之的纪律是：**一次改动只做一件事，且这一个提交可以单独回退**。
- 上游继承来的类型错误成为我们的债，可以修；`pnpm typecheck` 的目标从「忽略 57 个上游错误」变成「零错误」，而不是给它们建永久白名单。
- 上游继承来的风格（4 空格、单引号）不再有保护价值。何时统一到 prettier 由单独决定，不与功能改动混在同一个提交里。
- 我们承担上游 bug 的修复责任：没有别人会替我们修。
- 保留 `upstream` remote，仅用于对照、查看单点修复的 diff、以及可选地 `git cherry-pick` 某个独立提交。**不作为合并来源**。
- 代码布局仍沿用上游（`src/provider/`、`src/react/view/<viewer>/`）：这不是对上游的承诺，而是它本来就合理，重排的收益不足以支付认知成本。偏离布局需要一条新 ADR。
- ADR-0001 关于「为什么 fork 而不是新建 slim 扩展」「身份必须独立」「telemetry 必须摘除」的结论继续有效，仅「可合并性」这一条被本 ADR 取代。
