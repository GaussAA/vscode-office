# 表格预览的体积上限：超过就先问，不先解析

表格预览是全量加载的：整份文件读成 `ArrayBuffer`，再变成「每个单元格一个对象」的网格。实测
（构建产物 + 无头 Chrome，数字见 `docs/agents/perf.md`）：

| 文件                        | 首屏   | 峰值 JS 堆 |
| --------------------------- | ------ | ---------- |
| 152 MB / 200 万行 CSV       | 9.7 s  | 1.36 GB    |
| 37 MB / 50 万行 CSV         | 2.6 s  | 331 MB     |
| 19 MB / 5 万行 × 10 列 xlsx | 10.0 s | 235 MB     |

峰值内存约是文件大小的 9 倍，而 webview 只是渲染进程里的一个标签页——它会像标签页一样被
杀掉，用户丢掉的是已经打开的编辑器。所以规则是：**CSV/TSV 超过 25 MB、xlsx/xlsm/xls/ods
超过 15 MB 时，先显示拒绝面板，由用户决定是否继续**。

拦截发生在两处，共用 `src/common/previewLimit.ts` 里的同一组常量，两端不会各说各话：

- **webview**：本地 `file:` 文件在 `fetch` 之前就被拦住（远程工作区里，下载本身就是一半成本）；
- **宿主**：虚拟文档（`vscode-vfs:`、`git:`）在读取之前就被拦住，因为那份字节要以
  `number[]` 走 `postMessage`，代价发生在解析之前。

「仍然打开」会绕过闸门：本地文件由 webview 自己 `fetch`，虚拟文档则通过 `openForce` 让宿主
重读一次并发送字节。

## Considered Options

- **只提示、不拦**：152 MB 的 CSV 仍然会走到 1.36 GB，标签页照样会被杀掉；提示救不了它。
- **先做流式/Worker 解析，不加闸**：方向对，但工作量大（表格模型、查找、排序都要窗口化），
  而且解决不了「webview 里同时持有 1.4 GB」这件事——上限仍然需要。
- **按单元格数而不是字节数判断**：更准，但只有解析完才知道；闸门必须在解析之前生效。

## Consequences

- 门槛是**常量**，不是设置项。要改就改代码 + 本 ADR；不提供「关掉闸门」的配置，因为它的失败
  模式是渲染进程崩溃，而不是变慢。
- 超过上限的文件多一次点击。CSV/TSV 额外给「在 VS Code 中打开」——文本编辑器对它们本来就是
  可用路径；xlsx 没有等价的宿主能力，只保留「仍然打开」。
- 这不是流式解析的替代：25 MB 以下的 CSV 仍然是全量加载 + 全量网格。将来把表格模型窗口化时，
  这个常量应该随之上调，而不是被删掉。
